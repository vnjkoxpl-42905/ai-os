## The four interview methods, and when each earns its keep

**`grilling`**: the engine. Builds a decision tree, asks every currently-answerable question in one round with a recommendation under each, waits, repeats. Looks up facts itself. Nothing persisted. Use directly only for a throwaway.

**`grill-me`**: `grilling` + durable capture into the vault. Use for anything open-ended: business decisions, priorities, "what should the next month look like", extracting what's in your head. This is your default.

**`grill-with-docs`**: `grilling` + `domain-modeling`. Same interview, but every question is checked against `CONTEXT.md` (your glossary and domain model) and every decision that crystallises is written as an ADR in `decisions/`. Use when the topic is a *system* with named parts: the LSAT U classroom, the booking flow, the RRC pipeline. The payoff is that fuzzy terms get pinned ("what exactly is a Section resume row?") and the docs stay honest as a side effect. Note it does **not** write a brainstorm capture; the docs *are* the capture. If you want both, run `/grill-with-docs` and tell it to also checkpoint to `brainstorms/`.

**`brainstorming`** (Superpowers): not a grill. It's a gate before *implementation*: explore intent, produce a written design doc, get your approval, then hand off to a plan. One question at a time, fewer questions, ends in a document a coder can execute. Use when the destination is code within the hour. Your `grill-me` already cross-references it for exactly that case.

So for the thing you said, "good for brainstorming": if you mean thinking something through, `grill-me`. If you mean shaping a feature that touches named concepts in LSAT U, `grill-with-docs`. If you mean "I know what I want, design it so we can build it", `brainstorming`.
