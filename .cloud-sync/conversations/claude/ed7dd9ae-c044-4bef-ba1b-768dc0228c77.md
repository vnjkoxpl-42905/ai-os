## 7. Where the plan was wrong

Six places. Each was verified before being set aside.

1. **WP-F's premise is false.** `ThemeContext` adds `.light` and removes it; dark is the *absence* of a class. `classroom.css` keys its entire dark palette on `html.dark`, which nothing in the app ever sets, so 22 dark rules are dead code. 2. **The theme class is `html.dark` in CSS but `.light` in the app.** The plan's Part 0 table says `.light`; both are half right, and the mismatch is the bug above.
3. **WP-K step 2 describes an unreachable state.** `resolveItemRoute` returns a string on every branch and notifications always carry `onOpen`, so the hero CTA can never be disabled. Writing a reason sentence for it would be dead copy.
4. **WP-J's "define a scale" was already done.** A seven-step scale exists at `classroom.css:954`. The defect is literals bypassing it, not its absence, and the plan's proposed replacement values would have moved every size on the page.
5. **The 1a scan has a second blind spot, and it is structural.** The plan's caveat covers photographs. It does not cover the other case, which fires on the default stage every time: `bgOf` walks *ancestors* for a background colour, so any text sitting on an absolutely positioned **sibling** is measured against whatever is behind that sibling instead. The section switch's active label reports 1.06:1 and is actually 11.79:1. Both blind spots are the same mistake at bottom, which is that the scan reads the CSS cascade rather than the pixels. Text over a photograph, a gradient, a sibling, a `::before` or a canvas needs sampling, and nothing in the scan's output tells you which case you are in. Treat a 1a fail as a question, not an answer.
6. **1c's width test cannot pass in the in-app browser at all.** A `div` created on the spot with `border: 2px solid` reports `1.6px` from `getComputedStyle` while its `height: 20px` reports exactly 20. Every outline, offset and border width in that pane is scaled by 0.8 before it is reported, so `parseFloat(cs.outlineWidth) >= 2` is never true and 1c flags every control on the page. This is on top of the `:focus-visible` over-reporting the plan already warns about, and it is the larger of the two effects. The check that works: press Tab once for real to arm the keyboard heuristic, then read `outline-style` and `box-shadow` rather than any width, and take the width from the source. Done that way, all 14 focusable controls resolve to a solid outline or a 2px inset ring, and the shipped CSS declares `2px` on every hub focus rule.

## Hard rules

1. **Chat output only.** Never write the handoff to a file. Never update memory from this skill. (That is `wrapup`'s job, not this one.)
2. **Never invent state.** If a section has nothing to report, write "none" — do not omit the section. Structure stability is the whole point.
3. **Absolute paths always.** The next agent may have a different working directory, or be Codex.
4. **If a plan file drove the session, name it first** in "Key files" so the next agent reads it before anything else.
5. **No emojis, no hype, no "great job" summaries.** Terse and concrete — paths, commands, shell IDs, decisions. Tone of a seasoned engineer handing off at end-of-shift.
6. **Background process IDs are critical.** If you started any `run_in_background` shells, their IDs must appear in "Running state" with the kill command — the next agent cannot find them otherwise.
7. **Stamp verified state, and separate it from assumed state.** Run `date "+%H:%M"` and use the real time. Every claim about live systems (deploy status, DB contents, what was sent, what is published) is either something you actually checked this session — say how — or explicitly marked NOT re-verified. A handoff that presents stale belief as current state makes the next session re-derive everything, which is the exact cost this skill exists to remove.
8. **Open questions are obligations, not notes.** Anything under OPEN must be resolved by the next session or re-asked to Joshua before it starts new work. Requirements have been silently re-typed across sessions, and a promised artifact once never arrived because nobody re-asked. If a question was open in the handoff you are picking up from, it is the first thing you raise.

## Anti-patterns — do not do these

- Summarizing the last 3 turns and calling it a handoff.
- Listing files by relative path.
- Skipping "Running state" because "nothing is running" — write "none" instead.
- Writing the summary to any file. This is chat-only by design.
- Adding a "what went well / what went poorly" retrospective. This isn't a retro.
- Recommending next steps beyond the single "Pick up here" line. The next agent decides; you just hand off.
