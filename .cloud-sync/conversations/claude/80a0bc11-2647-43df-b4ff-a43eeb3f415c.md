## The command

```

```

Flags: `--schedule YYYY-MM-DD` unlocks the work that morning. `--dry-run`
resolves the student and the work and writes nothing — use it when the name is
at all uncertain.

To pace a student over several days, run the command once per day with a
`--schedule` on each. Each run is its own assignment, its own row, and its own
email, so she is told about each day rather than handed a block.

Every assignment lands on the home calendar strip and the cell opens that
assignment — scheduled work on its unlock day, unscheduled work on the day you
assigned it. Nothing needs to be written by hand to put work on the calendar;
if an assignment is missing from the band, that is a bug to fix in
`useClassroomHome`, not something to patch into `classroom_items`.

Always `--dry-run` first for a student you have not assigned to before in this
session. It costs one second and it is the only cheap way to catch a wrong
account.

## Why a script and not a direct DB write

`scripts/assign.ts` calls the app's **own** `assignWork()` from
`src/lib/assignWork.ts`. Assigning touches seven tables — the assignment
snapshot, `classroom_items`, the conversation and its participants, `messages`,
`notifications` — plus the email edge function, and it rolls the whole thing
back if the classroom item or notify throws. There is no RPC and no edge
function for it; it is client-side code.

So never hand-write these rows. A second implementation drifts from the UI the
first time the app changes, and produces assignments subtly unlike the ones
Joshua makes by clicking.

## Failure modes

**`duplicate key … activity_assignments_active_unique`** — she already holds an
active assignment for this Activity. Not a bug; the DB refusing a double-assign.
Check what she has before re-trying (below).

**`"X" is ambiguous`** — the script lists every matching account and stops.
Pick the full name or the email. Never guess: a misdirected assignment is
silent, because she simply never sees it.

**Sign-in failed** — the credentials in `~/ai-os/.env` are wrong or the account
gained MFA.

/** The clock this run starts under. */
export function timerConfigForRunSpec(
  spec: DrillRunSpec | null | undefined,
): DrillTimerConfig | null {
  if (spec?.isGuidedDrill && spec.guidedDurationMinutes) {
    return { mode: 'countdown', durationMs: spec.guidedDurationMinutes * 60 * 1000 };
  }

  if ((spec?.mode === 'type-drill' || spec?.mode === 'practice-set') && spec.config) {
    const config = spec.config as TypeDrillConfig;
    if (config.selectedQids && config.selectedQids.length > 0) {
      return { mode: 'stopwatch' };
    }
  }

  if (spec?.mode === 'full-section' && spec.config) {
    const timer = (spec.config as FullSectionConfig).timer as TimerConfig;

    if (timer.mode === 'unlimited') {
      return { mode: 'stopwatch' };
    }

    let durationMs: number;
    switch (timer.mode) {
      case '35':
        durationMs = 35 * 60 * 1000;
        break;
      case '52.5':
        durationMs = 52.5 * 60 * 1000;
        break;
      case '70':
        durationMs = 70 * 60 * 1000;
        break;
      case 'custom':
        durationMs = (timer.customMinutes || 35) * 60 * 1000;
        break;
      default:
        durationMs = 35 * 60 * 1000;
    }

    return { mode: 'countdown', durationMs };
  }

  return { mode: 'stopwatch' };

/** Whatever the URL already said that a launch has no opinion about. */
function mergeUnclaimedParams(canonical: string, existing: URLSearchParams): string {
  const merged = new URLSearchParams(canonical);
  existing.forEach((value, key) => {
    if (!merged.has(key)) merged.set(key, value);
  });
  return merged.toString();
}

export default function DrillLaunchGate({ children }: Props) {
  const [searchParams] = useSearchParams();
  const location = useLocation();
  const navigate = useNavigate();
  const { user } = useAuth();
  const { isLoading: questionBankLoading } = useQuestionBank();
  const [failure, setFailure] = React.useState<string | null>(null);
  const [resolved, setResolved] = React.useState<{ key: string; spec: DrillRunSpec } | null>(
    null,
  );

  const namedInUrl = !!searchParams.get('drill') || !!searchParams.get('mode');

  const { launch, parseError } = React.useMemo<{
    launch: DrillLaunch | null;
    parseError: string | null;
  }>(() => {
    try {
      const fromUrl = parseDrillLaunch(searchParams);
      if (fromUrl) return { launch: fromUrl, parseError: null };
    } catch (error) {
      return {
        launch: null,
        parseError:
          error instanceof DrillLaunchError
            ? error.message
            : 'That drill link could not be opened.',
      };
    }

    // Nothing in the address bar. What a button passed in memory, if anything.
    const routeState = location.state as (DrillHandoverState & { ptRun?: PtLegRef }) | null;
    const fromState = launchFromRouteState(routeState, routeState?.ptRun);
    if (!fromState) return { launch: null, parseError: null };
    // Some callers put the way back in the query string rather than in state
    // (`/drill?returnTo=/flagged`). Carry it onto the launch or the exit falls
    // back to Classroom Home.
    const queryReturnTo = searchParams.get('returnTo');
    if (queryReturnTo && !fromState.options?.returnTo) {
      return {
        launch: {
          ...fromState,
          options: { ...(fromState.options ?? {}), returnTo: queryReturnTo },
        },
        parseError: null,
      };
    }
    return { launch: fromState, parseError: null };
  }, [searchParams, location.state]);

  // Stable name for this run. The rewrite below produces the same key, which is
  // what stops the effect from resolving the same launch a second time.
  const launchKey = React.useMemo(() => (launch ? launchDrill(launch) : null), [launch]);

  const needsResolution = !!launch && launchNeedsResolution(launch);
  const waitsForQuestionBank =
    needsResolution && (launch.kind === 'bootcamp-day' || launch.kind === 'guided-drill');

  // The kinds that carry their own questions need no round trip, so they start
  // without a spinner.
  const syncSpec = React.useMemo(
    () => (launch && !needsResolution ? drillRunSpecFromLaunch(launch) : null),
    [launch, needsResolution],
  );

  React.useEffect(() => {
    if (!launch || !launchKey) return;
    if (!needsResolution) return;
    if (resolved?.key === launchKey) return;
    if (waitsForQuestionBank && questionBankLoading) return;
    let cancelled = false;

    const run = async () => {
      try {
        const qids = await resolveDrillLaunch(launch, user?.id);

        if (launch.kind === 'bootcamp-day' && user?.id && qids?.length) {
          void recordExposures(user.id, qids).catch((error) => {
            console.error('[DrillLaunchGate] recordExposures failed', error);
          });
        }

        if (cancelled) return;
        setResolved({ key: launchKey, spec: drillRunSpecFromLaunch(launch, qids) });
      } catch (error) {
        if (cancelled) return;
        setFailure(
          error instanceof DrillLaunchError
            ? error.message
            : 'That drill link could not be opened.',
        );
      }
    };

    void run();
    return () => {
      cancelled = true;
    };
  }, [
    launch,
    launchKey,
    needsResolution,
    resolved?.key,
    waitsForQuestionBank,
    questionBankLoading,
    user?.id,
  ]);

  // A handover with nothing in the address bar gets one written for it, so the
  // next refresh has something to rebuild the run from.
  React.useEffect(() => {
    if (namedInUrl || !launchKey) return;
    navigate(
      { pathname: '/drill', search: mergeUnclaimedParams(launchKey, searchParams) },
      // `state: null` is load-bearing: it is what stops this effect from seeing
      // the same handover again and rewriting forever.
      { replace: true, state: null },
    );
  }, [namedInUrl, launchKey, searchParams, navigate]);

  const spec = syncSpec ?? (resolved?.key === launchKey ? resolved.spec : null);

  if (failure || parseError) {
    return (
      <div className="min-h-screen flex items-center justify-center bg-background px-6">
        <div className="max-w-md text-center space-y-4">
          <h1 className="text-xl font-semibold text-foreground">This drill isn't available</h1>
          <p className="text-sm text-muted-foreground">{failure ?? parseError}</p>
          <Button onClick={() => navigate('/classroom')}>Back to classroom</Button>
        </div>
      </div>
    );
  }

  if (launch && !spec) {
    return (
      <div className="min-h-screen flex items-center justify-center bg-background">
        <div className="flex items-center gap-3 text-sm text-muted-foreground">
          <Loader2 className="h-4 w-4 animate-spin" aria-hidden />
          Opening your drill…
        </div>
      </div>
    );
  }

  return <DrillRunSpecProvider spec={spec ?? EMPTY_SPEC}>{children}</DrillRunSpecProvider>;
}

# Session Handoff

Produce a repeatable end-of-session summary so Joshua can `/clear` and start a fresh agent without losing continuity. The next agent should pick up by reading this summary alone.

This is a **context-handoff artifact**, not a status report. The audience is a future instance of you, not a stakeholder.

**Handoff vs. wrapup:** run `session-handoff` when the *context window* is the problem — nearing ~250k tokens (the dumb zone), or passing work between Claude and Codex. It is chat-only and writes nothing. Run `wrapup` when the *work day* is done — it strikes tasks, refreshes `wiki/hot.md`, and appends `wiki/log.md`. They can be run back to back (wrapup to persist, then handoff to reset).

## When to invoke

Joshua says: "session handoff", "hand off", "handoff summary", "summarize before I clear", or any near-equivalent. Note "let's wrap up" belongs to `wrapup`, not here — if he says that and the context window is also deep, run `wrapup` first, then offer this. Also invoke proactively if he says he's about to `/clear` without having run it, or if the session is clearly deep into the dumb zone.

## How to produce the summary

1. **Review the full conversation**, not just the last few turns. Handoffs miss things when they only summarize recent context.
2. **Pull state from these sources (in order):**
   - Plan files referenced this session (check `~/.claude/plans/` if a plan was mentioned).
   - TodoWrite state — any in-progress or pending tasks.
   - Background processes started with `run_in_background` — shell IDs are load-bearing for the next agent.
   - Files created or modified this session — you know what you touched; don't grep to re-discover.
   - Memory files written or updated (`~/.claude/projects/C--Users-Joshu-dev-ai-os/memory/`).
   - Unresolved questions — things you asked Joshua that never got a clear answer, or things he asked that got deflected.
3. **Do NOT audit the filesystem.** This is synthesis of what happened in THIS session. No `git log`, no broad `Glob` sweeps. If you didn't touch it this session, it doesn't belong here.
4. **Produce the output in chat.** Do not write a file. Do not update memory. Chat-only.

## Hard rules

1. **Chat output only.** Never write the handoff to a file. Never update memory from this skill. (That is `wrapup`'s job, not this one.)
2. **Never invent state.** If a section has nothing to report, write "none" — do not omit the section. Structure stability is the whole point.
3. **Absolute paths always.** The next agent may have a different working directory, or be Codex.
4. **If a plan file drove the session, name it first** in "Key files" so the next agent reads it before anything else.
5. **No emojis, no hype, no "great job" summaries.** Terse and concrete — paths, commands, shell IDs, decisions. Tone of a seasoned engineer handing off at end-of-shift.
6. **Background process IDs are critical.** If you started any `run_in_background` shells, their IDs must appear in "Running state" with the kill command — the next agent cannot find them otherwise.
7. **Stamp verified state, and separate it from assumed state.** Run `date "+%H:%M"` and use the real time. A handoff that presents stale belief as current state makes the next session re-derive everything, which is the exact cost this skill exists to remove.
8. **Open questions are obligations, not notes.** Anything under OPEN must be resolved by the next session or re-asked to Joshua before it starts new work. If a question was open in the handoff you are picking up from, it is the first thing you raise.

- Summarizing the last 3 turns and calling it a handoff.
- Listing files by relative path.
- Skipping "Running state" because "nothing is running" — write "none" instead.
- Writing the summary to any file. This is chat-only by design.
- Adding a "what went well / what went poorly" retrospective. This isn't a retro.
- Recommending next steps beyond the single "Pick up here" line. The next agent decides; you just hand off.
